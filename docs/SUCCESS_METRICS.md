# Success Metrics — как измеряем полезность App_ABC

Дата: 2026-08-19

## 1. Зачем этот документ

Нельзя считать приложение успешным только потому, что оно запускается и ребёнок нажимает правильные кнопки. Нужны измеримые признаки того, что связь `буква → название` становится устойчивее.

Метрики ниже используются для семейного пилота и не являются медицинской диагностикой.

## 2. Основные единицы измерения

Каждая попытка должна сохранять минимум:

- targetLetter;
- selectedLetter;
- isCorrect;
- responseTimeMs;
- timestamp;
- levelId;
- exerciseType;
- sessionId.

Желательно также хранить версию учебной политики `learningPolicyVersion`, чтобы позднее понимать, при каком алгоритме получены данные.

## 3. Главные метрики

### M1. Recent accuracy по букве

Доля правильных ответов в последних N валидных попытках по конкретной букве.

Использование:

- оценка текущего освоения;
- определение слабых букв;
- решение о повышении mastery state.

Для первой реализации N = 10, если данных достаточно.

### M2. Response time

Медианное время от предъявления задания до ответа.

Важно использовать медиану, а не только среднее: единичное отвлечение ребёнка не должно искажать картину.

Снижение времени при сохранении точности считается положительной динамикой.

### M3. Delayed success внутри сессии

Буква считается вспомненно закреплённой в рамках сессии, если после правильного ответа она снова правильно определяется после нескольких других заданий, а не только сразу повторно.

Минимальный критерий для первой версии:

- между предъявлениями было не менее 2 других заданий;
- повторный ответ правильный.

### M4. Межсессионное удержание

Когда накопится достаточно данных, отдельно считать точность по букве после реального перерыва.

Окна:

- `6h+` — короткое удержание;
- `24h+` — следующая длительная проверка;
- `7d+` — долгосрочное удержание.

Если нужного интервала ещё не было, метрика имеет статус `insufficient data`, а не 0%.

### M5. Confusion rate

Для каждой пары:

`targetLetter -> selectedWrongLetter`

считать количество и долю повторяющихся ошибок.

Пример: `Н -> П` встречается значительно чаще других ошибок по Н — это отдельная устойчивая путаница.

### M6. Stable letters

Количество букв, достигших состояния `STABLE` по текущей версии LearningPolicy.

Эта метрика полезнее общего количества открытых уровней: открыть букву можно быстро, устойчиво запомнить — нет.

## 4. Метрики сессии

На родительском экране можно показывать:

- число заданий;
- общую точность;
- медианное время ответа;
- какие буквы дали ошибки;
- какие ошибки повторились;
- новые/изучаемые/stable буквы;
- изменение относительно предыдущих сессий.

Не использовать общий балл как единственную оценку.

## 5. Критерии полезной динамики

Положительная динамика по букве фиксируется, если наблюдается хотя бы одно из следующего без ухудшения других ключевых показателей:

- recent accuracy растёт;
- медианное время ответа снижается;
- confusion rate снижается;
- правильные ответы сохраняются после более длинных интервалов;
- буква переходит `LEARNING -> FAMILIAR -> STABLE`.

## 6. Минимальный критерий для перехода в STABLE

До отдельной валидации использовать LearningPolicy v1:

- минимум 10 валидных попыток по букве;
- recent accuracy >= 90%;
- минимум 2 правильных delayed-проверки внутри разных участков сессии;
- нет 2 ошибок подряд в последних 5 попытках;
- при наличии межсессионных данных — хотя бы один правильный ответ после перерыва 6h+.

Если межсессионных данных ещё нет, статус может быть `FAMILIAR`, но не окончательно `STABLE`.

Эти пороги должны быть централизованной конфигурацией и иметь версию.

## 7. Критерий проблемной буквы v1

Буква попадает в «Трудные», если выполнено хотя бы одно:

- минимум 5 попыток и recent accuracy < 80%;
- минимум 2 ошибки в последних 5 попытках;
- одна и та же confusion pair повторилась >= 2 раз;
- медианное время ответа значительно выше личной медианы по знакомым буквам.

Последний критерий сначала использовать осторожно и не делать единственным основанием.

## 8. Метрики, которыми нельзя злоупотреблять

Не использовать как доказательство обучения сами по себе:

- число открытых уровней;
- количество кликов;
- число минут в приложении;
- серия дней;
- количество звёзд;
- количество пройденных сессий.

Это показатели активности/мотивации, а не знания.

## 9. Baseline

Когда основной тренажёр станет пригоден для реального использования, до активного обучения полного набора желательно провести короткую стартовую проверку:

- несколько заранее выбранных букв;
- одинаковый формат задания;
- без дополнительного обучения между вопросами;
- фиксировать точность и время ответа.

Baseline нужен только для сравнения динамики и не должен превращаться в стрессовый тест.

## 10. Product decision gate

Решение о расширении приложения до публичного продукта принимается не только по технической готовности. Перед этим должны быть:

- стабильный основной сценарий;
- накопленная история реального использования;
- понятные случаи улучшения/неулучшения;
- подтверждение, что метрики интерпретируются корректно;
- отсутствие очевидных игровых способов «обмануть» упражнение.
