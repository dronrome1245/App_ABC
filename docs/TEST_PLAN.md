# Test Plan — App_ABC

Дата: 2026-08-19

## 1. Два уровня проверки

Проект проверяется одновременно как:

1. **техническое приложение** — сборка, сохранение данных, алгоритм, UI;
2. **учебный инструмент** — не создаёт ли ложное ощущение знания и появляется ли реальная положительная динамика.

## 2. M1 acceptance test

Владелец должен суметь:

1. открыть приложение;
2. нажать «Начать»;
3. услышать запрос буквы;
4. повторить запрос;
5. нажать А или М;
6. увидеть спокойную реакцию;
7. пройти 10 вопросов;
8. увидеть X/10;
9. закрыть приложение;
10. открыть снова и убедиться, что история сохранена.

Дополнительно обязательно проверить:

- позиции `А` и `М` меняются между вопросами;
- правильный ответ нельзя угадывать по постоянному месту;
- одна цель не повторяется чрезмерно подряд;
- после ошибки буква возвращается спустя другие вопросы;
- TTS произносит именно название буквы;
- двойное нажатие не создаёт две Attempt;
- поворот/сворачивание приложения не приводит к очевидному сбою сессии.

## 3. После домашнего теста фиксировать

- размер кнопок;
- слышимость и корректность TTS;
- скорость смены вопроса;
- понятность ошибки;
- комфортное число вопросов;
- начинает ли ребёнок искать закономерность в расположении;
- появляется ли раздражение из-за повторов;
- требуется ли пауза между ответом и новым вопросом.

Наблюдения, требующие изменения продукта, фиксировать в Issue/DECISIONS/RISK_REGISTER в зависимости от масштаба.

## 4. Автотесты LearningEngine минимум

- старая буква не исчезает после открытия новой;
- retry возвращает ошибочную букву;
- retry не зацикливается;
- нет запрещённой длинной серии одного target;
- weak letter получает повышенный вес;
- strong letter сохраняет ненулевой шанс;
- confusion pair формируется правильно;
- история старых уровней не удаляется;
- при фиксированном seed тестовый сценарий воспроизводим;
- изменение LearningPolicy version не происходит неявно.

## 5. Persistence tests

После появления Room проверить:

- Attempt сохраняется;
- sessionId сохраняется;
- timestamp сохраняется;
- responseTime не отрицательный;
- приложение переживает обычный restart;
- обновление данных одной буквы не удаляет другую;
- destructive migration не используется молча;
- после появления migrations есть отдельные migration tests.

## 6. UX anti-cheat tests

### Позиционный тест

Провести серию вопросов, в которой правильный ответ случайно меняет положение.

Если точность резко отличается при перестановке, проверить риск R1.

### Тест угадывания

На уровне с двумя вариантами не считать несколько случайных правильных ответов доказательством mastery.

Проверить, что критерии из `SUCCESS_METRICS.md` требуют большего числа наблюдений и delayed success.

### Тест повторения

После ошибки target должен появиться снова, но не немедленно много раз подряд.

## 7. Product validation protocol

### Этап A — Baseline

Когда приложение будет готово к реальному пилоту:

- выбрать небольшой набор букв;
- дать одинаковый формат проверки;
- фиксировать accuracy и response time;
- не превращать baseline в длинный экзамен.

### Этап B — регулярное использование

- короткие сессии;
- не принуждать к продолжению после рекомендованной порции;
- приложение доступно повторно в тот же день;
- сохранять реальные интервалы между сессиями.

### Этап C — delayed comparison

Когда появляются интервалы 6h+, 24h+, 7d+, сравнивать:

- accuracy;
- response time;
- confusion rate;
- сохранение mastery.

Если нужного интервала ещё не было, вывод не делать.

## 8. Что НЕ считать доказательством успеха

Сами по себе не подтверждают обучение:

- 100% в одной короткой серии;
- много пройденных уровней;
- много минут в приложении;
- звёзды;
- серия дней;
- повтор одной буквы сразу после подсказки.

## 9. Проверка статистики для взрослого

До завершения M3 взрослый должен суметь без технических знаний ответить по экрану приложения:

- какие буквы знает лучше;
- какие труднее;
- с чем конкретная буква путается;
- растёт или падает точность;
- меняется ли время ответа;
- хватает ли данных для вывода.

## 10. Speech recognition test

До включения ASR в основной контур:

- минимум несколько произнесений одной буквы;
- несколько разных букв;
- тихая комната;
- обычный бытовой шум;
- raw recognition result виден взрослому в test screen;
- считаются ложные отказы и ложные принятия;
- `NOT_RECOGNIZED` не считается учебной ошибкой.

## 11. Release regression

Перед каждым milestone/tag проверить минимум:

- launch;
- start session;
- TTS;
- ответ correct/wrong;
- save/restart;
- result;
- statistics, когда появится;
- reset data, когда появится;
- отсутствие crash в основном потоке.

Критерии завершения каждого этапа брать из `DEFINITION_OF_DONE.md`.
