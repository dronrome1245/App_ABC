# Development Workflow — vibe coding без потери управляемости

Дата: 2026-08-19

## 1. Источник истины

GitHub-репозиторий — единственный источник текущего состояния проекта.

Нормативная иерархия:

1. последнее явное решение владельца;
2. `docs/DECISIONS.md`;
3. `docs/PRODUCT_CHARTER.md`;
4. `docs/PRODUCT_SPEC.md`;
5. `docs/LEARNING_ENGINE.md` / `docs/CURRICULUM.md`;
6. `docs/DEFINITION_OF_DONE.md`.

Операционные документы:

- `docs/BACKLOG.md` — roadmap;
- `PROJECT_STATUS.md` — фактическое состояние;
- `NEXT_TASK.md` — одна ближайшая задача;
- GitHub Issues/PR — исполняемые единицы работы.

При конфликте новое явное решение владельца имеет приоритет и должно быть отражено в `DECISIONS.md`.

## 2. Код не переписывает продуктовые решения

Фактический код показывает, **что реализовано**, но не создаёт автоматически новое решение о том, **как должно быть**.

Если код расходится с нормативными документами, это `implementation drift`.

Порядок работы с drift:

1. выявить точное отличие;
2. проверить, было ли явное решение владельца;
3. если решение есть — синхронизировать код и документацию с ним;
4. если решения нет — не менять нормативную документацию под случайный код;
5. вынести владельцу один конкретный выбор или вернуть реализацию к ранее принятой спецификации, если это явно поручено.

## 3. Обязательный AI Preflight

До выдачи и до исполнения task packet необходимо проверить:

- актуальные source-of-truth документы;
- фактический код, если он релевантен;
- milestone scope;
- `DEFINITION_OF_DONE.md`;
- наличие решения владельца для новых продуктовых параметров;
- различия tests/build/emulator/physical device/owner acceptance;
- отсутствие scope creep.

Task packet не считается новым источником истины.

Gemini Web обязан сделать preflight до выдачи задания. ChatGPT обязан независимо сверить задание с репозиторием до изменений.

Если task packet содержит самовольное продуктовое решение, оно не выполняется и помечается `OWNER_DECISION_REQUIRED`.

## 4. Правило одной следующей задачи

`NEXT_TASK.md` содержит только одну ближайшую техническую задачу или один законченный milestone slice.

AI не должен переходить к следующему milestone автоматически.

После завершения:

- обновить `PROJECT_STATUS.md`;
- отметить выполненное в `BACKLOG.md`;
- подготовить новый `NEXT_TASK.md` только после проверки текущего результата или явного указания владельца.

## 5. GitHub Issues

После появления активной разработки использовать Issues для конкретных задач/дефектов.

Рекомендуемые типы заголовков:

- `[Feature] ...`
- `[Bug] ...`
- `[Learning] ...`
- `[UX] ...`
- `[Tech] ...`
- `[Risk] ...`

`BACKLOG.md` остаётся roadmap верхнего уровня; Issues — исполняемые единицы работы.

Не создавать Issue на каждую мелкую правку текста.

## 6. Ветки

После появления Android-кода:

- `main` — всегда рабочая ветка;
- каждая существенная кодовая задача — отдельная ветка;
- формат: `feature/...`, `fix/...`, `docs/...`, `refactor/...`;
- одна ветка = одна логическая задача.

Документационные guardrail-правки, не влияющие на runtime, допускаются напрямую в `main`.

## 7. Pull Request

После M1 кодовые изменения желательно вносить через PR.

PR должен содержать:

- цель;
- что изменено;
- что не изменено;
- результаты tests/build;
- ручные проверки владельца, если нужны;
- риски/ограничения;
- обновления документации;
- указание, менялись ли LearningPolicy/Curriculum и на основании какого решения.

Не объединять в один PR несвязанные функции.

## 8. CI

Когда Android-проект создан, необходимо добавить минимальный GitHub Actions workflow, если он ещё отсутствует.

Минимальный CI на PR и push в `main`:

- checkout;
- setup JDK;
- Gradle cache;
- unit tests;
- debug build.

Позднее можно добавить lint.

## 9. Merge policy

В `main` не merge, если:

- проект не компилируется;
- unit tests красные;
- основной сценарий заведомо сломан;
- есть незадокументированное изменение LearningPolicy/Curriculum;
- task packet содержит unresolved owner decision;
- изменение требует обязательной ручной acceptance-проверки текущего milestone, но она ещё не выполнена.

Для небольшого личного проекта формальное approval второго разработчика не требуется.

## 10. Milestone acceptance

Всегда отдельно фиксировать:

- implementation status;
- static review status;
- unit tests / CI status;
- local build status;
- emulator runtime status;
- physical-device runtime status;
- owner acceptance status.

`implementation complete` не означает `milestone complete`.

Если DoD требует физическое устройство, emulator не заменяет его.

Следующий milestone не стартует автоматически до прохождения обязательных gate, если владелец явно не изменил порядок работ.

## 11. Версии продукта

До первого публичного release использовать milestone-версии:

- `M1`, `M2`, ...;
- при необходимости теги `m1-pilot`, `m2-learning-engine`.

Перед Google Play перейти к app versioning, например `0.1.0`, `0.2.0`, `1.0.0`.

## 12. Версионирование учебной логики

Отдельно от версии приложения хранить:

- `learningPolicyVersion`;
- `curriculumVersion`;
- `databaseSchemaVersion`.

Это нужно, чтобы статистика не теряла смысл после изменений алгоритма.

## 13. Правило изменений LearningPolicy/Curriculum

AI не вправе самовольно менять:

- пороги mastery;
- состояния mastery, если они уже зафиксированы;
- веса слабых/старых/новых букв;
- retry interval;
- критерии открытия уровня;
- правила weak letters;
- состав/порядок curriculum;
- число вопросов или критерий прохождения, если это влияет на учебное поведение.

Если изменение требуется:

1. описать проблему;
2. предложить вариант как `PROPOSAL`;
3. указать влияние;
4. получить решение владельца;
5. добавить запись в `DECISIONS.md`;
6. повысить соответствующую версию при изменении поведения;
7. обновить тесты.

## 14. Маршрутизация AI

Следовать `docs/AI_ROLES.md`.

Приоритет:

1. `OWNER_SIMPLE_ACTION` — 1–5 простых действий;
2. `CHATGPT_REPOSITORY` — код/docs/GitHub/static review;
3. `ANDROID_STUDIO_AGENT` — только незаменимый IDE/runtime Android-контекст;
4. `OWNER_DECISION` — продуктовый выбор.

Commit/push/pull, обычный Run, pure Kotlin и JVM unit tests не являются поводом расходовать Android Studio Agent.

## 15. Откат

Если новая версия ухудшила основной сценарий или AI запустил опасную Git-операцию:

- остановить операцию;
- определить последний рабочий commit;
- не использовать Force Push в `main`;
- при необходимости восстановить рабочее дерево из `origin/main` по `docs/LOCAL_GIT_SYNC.md`;
- создать отдельную bug/tech-задачу, если проблема требует анализа;
- сохранить пользовательские данные, если затронута БД.

## 16. Что должен делать владелец

Владелец не обязан читать код или проверять техническую корректность task packet между AI.

Его обязательные действия только там, где нельзя заменить его роль:

- принять продуктовые решения;
- запустить приложение/выполнить простой Git UI шаг при необходимости;
- проверить UX на требуемом устройстве;
- сообщить наблюдаемое поведение;
- подтвердить milestone acceptance.

AI отвечает за код, документацию, preflight, техническую проверку и корректность маршрутизации.

## 17. Конец каждой AI-сессии

Перед завершением агент обязан ответить:

1. Что сделал?
2. Что проверил автоматически?
3. Каков точный acceptance-status?
4. Что действительно должен проверить владелец?
5. Изменились ли риски?
6. Обновлены ли status/backlog/decisions при необходимости?
7. Какой следующий шаг — но не выполнять его автоматически, если текущий gate не закрыт.
