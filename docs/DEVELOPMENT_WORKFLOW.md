# Development Workflow — vibe coding без потери управляемости

Дата: 2026-08-19

## 1. Источник истины

GitHub-репозиторий — единственный источник текущего состояния проекта.

Иерархия управленческих документов:

1. `docs/PRODUCT_CHARTER.md` — зачем существует продукт.
2. `docs/DECISIONS.md` — принятые решения.
3. `docs/PRODUCT_SPEC.md` — что входит в продукт.
4. `docs/DEFINITION_OF_DONE.md` — когда этап считается завершённым.
5. `docs/BACKLOG.md` — roadmap.
6. `PROJECT_STATUS.md` — фактическое состояние сейчас.
7. `NEXT_TASK.md` — одна ближайшая задача AI.

При конфликте новое явное решение владельца имеет приоритет, но должно быть отражено в `DECISIONS.md`.

## 2. Правило одной следующей задачи

`NEXT_TASK.md` содержит только одну ближайшую техническую задачу или один законченный milestone slice.

AI не должен переходить к следующему milestone автоматически.

После завершения:

- обновить `PROJECT_STATUS.md`;
- отметить выполненное в `BACKLOG.md`;
- подготовить новый `NEXT_TASK.md` только после проверки текущего результата или явного указания владельца.

## 3. GitHub Issues

После появления активной разработки использовать Issues для конкретных задач/дефектов.

Рекомендуемые типы заголовков:

- `[Feature] ...`
- `[Bug] ...`
- `[Learning] ...`
- `[UX] ...`
- `[Tech] ...`
- `[Risk] ...`

`BACKLOG.md` остаётся roadmap верхнего уровня; Issues — исполняемые единицы работы.

Не создавать Issue на каждую мелкую правку текста.

## 4. Ветки

Пока репозиторий содержит только документацию, изменения допускаются прямо в `main`.

После создания первого Android-проекта:

- `main` — всегда рабочая ветка;
- каждая существенная кодовая задача — отдельная ветка;
- формат: `feature/...`, `fix/...`, `docs/...`, `refactor/...`;
- одна ветка = одна логическая задача.

Примеры:

- `feature/m1-training-screen`
- `feature/learning-policy-v1`
- `fix/tts-repeat-button`

## 5. Pull Request

После M1 кодовые изменения желательно вносить через PR.

PR должен содержать:

- цель;
- что изменено;
- что не изменено;
- результаты тестов/build;
- ручные проверки владельца, если нужны;
- риски/ограничения;
- обновления документации.

Не объединять в один PR несвязанные функции.

## 6. CI

Когда Android-проект будет создан, в рамках M1/M2 необходимо добавить GitHub Actions workflow.

Минимальный CI на PR и push в `main`:

- checkout;
- setup JDK;
- Gradle cache;
- unit tests;
- debug build.

Позднее можно добавить lint.

До появления Gradle-проекта workflow не создаётся, чтобы репозиторий не имел заведомо падающего CI.

## 7. Merge policy

В `main` не merge, если:

- проект не компилируется;
- unit tests красные;
- основной сценарий заведомо сломан;
- есть незадокументированное изменение LearningPolicy/Curriculum;
- изменение требует ручной проверки, но владелец ещё не проверил критичный UX, если это milestone acceptance.

Для небольшого личного проекта формальное approval второго разработчика не требуется.

## 8. Версии продукта

До первого публичного release использовать внутренние milestone-версии:

- `M1`, `M2`, ...;
- при необходимости теги `m1-pilot`, `m2-learning-engine`.

Перед Google Play перейти к semantic-like app versioning, например `0.1.0`, `0.2.0`, `1.0.0`.

## 9. Версионирование учебной логики

Отдельно от версии приложения хранить:

- `learningPolicyVersion`;
- `curriculumVersion`;
- `databaseSchemaVersion`.

Это нужно, чтобы статистика не теряла смысл после изменений алгоритма.

## 10. Правило изменений LearningPolicy

AI не вправе самовольно менять:

- пороги mastery;
- веса слабых/старых/новых букв;
- retry interval;
- критерии открытия уровня;
- правила определения weak letters.

Если изменение требуется:

1. описать проблему;
2. предложить изменение;
3. указать ожидаемое влияние;
4. получить решение владельца, если оно меняет учебную механику;
5. добавить запись в `DECISIONS.md`;
6. повысить `learningPolicyVersion` при изменении поведения;
7. обновить тесты.

## 11. Откат

Если новая версия ухудшила основной сценарий:

- не пытаться бесконечно чинить поверх сломанного состояния;
- определить последний рабочий commit/tag;
- при необходимости откатить проблемное изменение;
- создать отдельную bug-задачу;
- сохранить данные пользователя, если проблема связана с БД.

## 12. Что должен делать владелец

Владелец не обязан читать код.

Его обязательные проверки:

- запустить приложение;
- проверить UX на реальном телефоне;
- сообщить наблюдаемое поведение;
- принять решения, влияющие на продукт/обучение;
- подтвердить milestone acceptance.

AI отвечает за код, сборку, тесты, документацию и техническое объяснение.

## 13. Конец каждой AI-сессии

Перед завершением агент обязан ответить:

1. Что сделал?
2. Что проверил автоматически?
3. Что должен проверить владелец?
4. Изменились ли риски?
5. Обновлены ли `PROJECT_STATUS`, `BACKLOG`, `DECISIONS` при необходимости?
6. Какой следующий шаг — но не выполнять его без команды, если текущий milestone требует ручной проверки.
