# AGENTS.md — обязательные правила для AI-разработчиков

Этот файл является инструкцией для любого AI-агента, который изменяет App_ABC: Gemini, Codex, Claude Code и других.

## Перед началом любой задачи

Обязательно прочитать:

1. `README.md`
2. `PROJECT_STATUS.md`
3. `docs/PRODUCT_CHARTER.md`
4. `docs/DECISIONS.md`
5. `docs/DEFINITION_OF_DONE.md`
6. `docs/RISK_REGISTER.md`
7. относящийся к задаче документ из `docs/`
8. `NEXT_TASK.md`, если выполняется ближайший этап

Не угадывать текущее состояние проекта по старому диалогу. Репозиторий — источник истины.

## Контекст владельца

Владелец проекта не является программистом и ведёт разработку методом vibe coding.

- не просить владельца вручную исправлять код, зависимости, Gradle или merge-конфликты, если агент может сделать это сам;
- объяснять действия обычным языком;
- давать владельцу только ручные действия, которые действительно требуют Android Studio, телефона, разрешений ОС или GitHub UI;
- если есть несколько равноценных технических вариантов, выбирать наиболее простой и объяснять выбор;
- продуктовые решения, влияющие на ребёнка, обучение, данные или scope, не принимать молча.

## Границы MVP

В MVP входят Android, Kotlin + Jetpack Compose, печатные заглавные русские буквы, название буквы без обучения звукам, уровни, адаптивное повторение, статистика, тренировка слабых букв, локальное хранение, родительский доступ к статистике/настройкам и короткие рекомендуемые сессии без суточной блокировки.

Не добавлять без отдельного решения владельца: слоги/слова, фонетику/звуки букв, рисование, распознавание почерка, iOS, backend/аккаунты/облако, рекламу, сложную игровую экономику и медицинские выводы.

Распознавание произношения — отдельный экспериментальный модуль после основного MVP.

## Технические правила

- Kotlin.
- Jetpack Compose + Material 3.
- Gradle Kotlin DSL.
- ViewModel + StateFlow.
- Room для истории попыток и статистики.
- DataStore для простых настроек.
- Учебный алгоритм держать в чистом Kotlin-коде, не смешивать с UI.
- UI-тексты — на русском; имена классов/методов — на английском.
- Не добавлять тяжёлые фреймворки и сервер без необходимости.
- После появления стабильной базы не использовать destructive migration реальных данных без явного решения.

## Обязательное версионирование учебной логики

После M1 должны существовать и сохраняться вместе с данными:

- `learningPolicyVersion`;
- `curriculumVersion`;
- `databaseSchemaVersion`.

AI не вправе самовольно менять:

- пороги mastery;
- веса слабых/новых/старых букв;
- retry interval;
- критерии открытия уровней;
- правила определения weak letters;
- порядок/правила curriculum.

Если поведение меняется — описать причину, обновить `DECISIONS.md`, повысить соответствующую версию и обновить тесты.

## Правила изменения проекта

Для каждой задачи:

1. Коротко сформулировать план.
2. Убедиться, что задача соответствует `NEXT_TASK.md`/Issue и scope milestone.
3. Сделать минимальный законченный кусок.
4. Запустить доступные проверки и тесты.
5. Не оставлять заведомо некомпилируемый код.
6. Не отключать тесты/lint ради зелёной сборки без объяснения.
7. Проверить `docs/DEFINITION_OF_DONE.md` для текущего этапа.
8. Просмотреть `docs/RISK_REGISTER.md` и обновить его, если появился новый риск или сработал триггер.
9. Обновить `PROJECT_STATUS.md`, если изменился этап или следующий шаг.
10. Обновить `docs/BACKLOG.md`, если изменился статус roadmap.
11. Обновить `docs/DECISIONS.md`, если принято новое продуктовое/архитектурное решение.
12. В отчёте владельцу указать: что сделано, что проверено, что ему нужно проверить на телефоне/в Android Studio, следующий шаг.

## Git workflow

После появления Android-кода следовать `docs/DEVELOPMENT_WORKFLOW.md`.

Главные правила:

- `main` должен оставаться рабочим;
- одна существенная кодовая задача — одна ветка;
- после M1 изменения кода желательно проводить через PR;
- не merge при красных тестах/build;
- CI добавить после появления Gradle-проекта, а не раньше.

## Учебная логика важнее игровой оболочки

Нельзя прекращать повтор старых букв после прохождения уровня, открывать новую букву только за количество нажатий, много раз подряд повторять ошибочную букву, считать серию одинаковых вопросов устойчивым знанием или строить обучение на жизнях/наказаниях.

Метрики активности (`уровни`, `звёзды`, `минуты`, `серия дней`) нельзя использовать как замену метрикам знания из `docs/SUCCESS_METRICS.md`.

## Curriculum и distractors

Следовать `docs/CURRICULUM.md`.

Важно:

- не фиксировать правильный ответ в одном месте экрана;
- перемешивать позиции;
- различать потенциально похожие и фактически путаемые буквы;
- фактическая confusion matrix имеет приоритет при персональной тренировке.

## Голосовой режим

До подтверждения качества распознавания детской речи:

- голосовой режим отдельно от основной mastery-логики;
- `не распознано` не считается неправильным ответом;
- не снижать прогресс из-за низкой уверенности ASR;
- не сохранять аудиозаписи без отдельного решения владельца;
- не запрашивать микрофон до явного входа в экспериментальный режим.

## Privacy

Следовать `docs/PRIVACY_RELEASE.md`.

Никогда не коммитить в публичный репозиторий:

- персональные данные ребёнка;
- аудиозаписи;
- локальную БД с реальной статистикой;
- signing keys;
- API keys/secrets.

## Критерий хорошего изменения

Владелец должен суметь получить изменения из GitHub, открыть проект в Android Studio, нажать Run, проверить функцию на телефоне и описать словами результат.

Задача считается законченной только при выполнении соответствующего Definition of Done либо при явной фиксации того, какой ручной acceptance-test ещё ожидается от владельца.
