# AGENTS.md — обязательные правила для AI-разработчиков

Этот файл является инструкцией для любого AI-агента, который изменяет App_ABC: ChatGPT, Gemini, Codex, Claude Code и других.

## Перед началом любой задачи

Обязательно прочитать актуальные версии:

1. `README.md`
2. `PROJECT_STATUS.md`
3. `docs/AI_ROLES.md`
4. `docs/PRODUCT_CHARTER.md`
5. `docs/DECISIONS.md`
6. `docs/DEFINITION_OF_DONE.md`
7. `docs/RISK_REGISTER.md`
8. относящийся к задаче документ из `docs/`
9. `NEXT_TASK.md`, если выполняется ближайший этап

Не угадывать текущее состояние проекта по старому диалогу. Репозиторий — источник актуального состояния.

## Контекст владельца

Владелец проекта не является программистом и ведёт разработку методом vibe coding.

- не просить владельца вручную исправлять код, зависимости, Gradle или merge-конфликты, если агент может сделать это сам;
- объяснять действия обычным языком;
- давать владельцу только ручные действия, которые действительно требуют Android Studio, телефона, разрешений ОС или GitHub UI;
- если есть несколько равноценных технических вариантов, выбирать наиболее простой;
- продуктовые решения, влияющие на ребёнка, обучение, данные, scope или acceptance, не принимать молча;
- владелец не должен выступать техническим посредником, который вручную перепроверяет task packet одного AI у другого.

## Обязательный Repository Preflight

Любой AI, получивший task packet, prompt или Issue, обязан **до внесения изменений** сверить его с актуальным репозиторием.

Нужно проверить:

1. соответствует ли задача текущему milestone;
2. нет ли конфликта между `DECISIONS`, `PRODUCT_SPEC`, `LEARNING_ENGINE`, `CURRICULUM`, `DEFINITION_OF_DONE` и фактическим кодом;
3. не выдаёт ли task packet случайное состояние кода за принятое решение;
4. не содержит ли task packet нового продуктового параметра без решения владельца;
5. не закрывает ли milestone без выполнения обязательного DoD;
6. не путает ли emulator, physical device, build/tests и owner acceptance;
7. не расширяет ли task packet scope без необходимости.

Task packet — **не новый источник истины**. Если task packet устарел или противоречит репозиторию, AI обязан исправить безопасную техническую часть самостоятельно и **не выполнять недопустимые продуктовые изменения**.

## Decision Firewall

Перед изменением любого из следующих параметров нужно установить источник решения:

- состав букв уровня;
- количество вопросов;
- критерий прохождения;
- mastery states/thresholds;
- weights;
- retry interval;
- level unlock;
- weak-letter criteria;
- Curriculum;
- Definition of Done;
- milestone gate;
- privacy/scope.

Допустимые источники:

`DECISION_SOURCE: OWNER` — явное решение владельца.

`DECISION_SOURCE: EXISTING_DECISION` — уже зафиксировано в `docs/DECISIONS.md` или нормативной спецификации.

Если источник отсутствует, изменение не выполняется. Требуется `OWNER_DECISION_REQUIRED`.

Запрещено:

- превращать `например 7/8` в правило;
- придумывать педагогическое обоснование от имени владельца;
- легализовать самовольный код простым обновлением документации;
- считать, что текущий код автоматически имеет приоритет над продуктовой спецификацией.

## Implementation Drift

Если код расходится с нормативной документацией, это implementation drift.

Порядок:

1. выявить точное расхождение;
2. проверить наличие решения владельца;
3. если решение есть — привести код/документацию к нему;
4. если решения нет — не менять нормативные документы под код;
5. запросить одно конкретное решение владельца либо вернуть код к уже принятой спецификации, если задание прямо это требует.

## Milestone Acceptance

Всегда различать:

- implementation complete;
- static review passed;
- tests/CI passed;
- local build passed;
- emulator runtime passed;
- physical-device runtime passed;
- owner acceptance passed.

Если `DEFINITION_OF_DONE.md` требует реальный телефон, эмулятор не закрывает этот gate.

Milestone нельзя помечать `COMPLETED`, пока все обязательные критерии DoD не подтверждены либо явно не перенесены решением владельца по правилу ниже.

## Обязательный Milestone Closure Evidence Audit

Перед любым действием вида `закрыть milestone`, `пометить DONE/100%`, `перейти к следующему milestone`, `merge release/closure PR` AI обязан **построчно** пройти соответствующий раздел `docs/DEFINITION_OF_DONE.md`.

Для каждого критерия нужно установить одно из состояний:

- `PASS — CODE`: функция непосредственно существует в актуальном коде;
- `PASS — TEST`: поведение подтверждено конкретным тестом;
- `PASS — CI/BUILD`: требование подтверждено CI/build;
- `PASS — RUNTIME`: требование подтверждено emulator/device run;
- `PASS — OWNER`: требование является именно субъективной/ручной приёмкой владельца и подтверждено владельцем;
- `DEFERRED_BY_OWNER — Dxxx`: владелец явно решил перенести критерий, решение записано в `docs/DECISIONS.md`, а требование добавлено в следующий milestone/backlog;
- `FAIL`;
- `UNKNOWN`.

Жёсткие правила:

1. `OWNER_ACCEPTANCE` **не доказывает наличие функции в коде**. Если критерий требует конкретную функцию (например per-letter result или retry queue), её наличие проверяется по коду/tests отдельно.
2. `CI PASS` не доказывает runtime/UX.
3. `код существует` не доказывает, что runtime прошёл.
4. Нельзя закрывать milestone при `FAIL` или `UNKNOWN`.
5. `DEFERRED_BY_OWNER` допустим только после явного решения владельца; AI не вправе переносить критерий сам.
6. При owner-approved переносе нельзя писать, что критерий `PASS`; нужно сохранить след в `DECISIONS.md`, `DEFINITION_OF_DONE.md`, `BACKLOG.md` и `NEXT_TASK.md`/следующем milestone.
7. Task packet на закрытие milestone обязан содержать краткую `DOD_AUDIT`/evidence matrix или явное подтверждение, что такая матрица была составлена по актуальному репозиторию.

Если task packet объявляет milestone завершённым, но не содержит/не подтверждает этот аудит, AI обязан считать это `PREFLIGHT_STOP_REPO_CONFLICT`, самостоятельно проверить DoD и не копировать заявленный статус.

## Границы MVP

В MVP входят Android, Kotlin + Jetpack Compose, печатные заглавные русские буквы, название буквы без обучения звукам, уровни, адаптивное повторение, статистику, тренировку слабых букв, локальное хранение, родительский доступ к статистике/настройкам и короткие рекомендуемые сессии без суточной блокировки.

Не добавлять без отдельного решения владельца: слоги/слова, фонетику/звуки букв, рисование, распознавание почерка, iOS, backend/аккаунты/облако, рекламу, сложную игровую экономику и медицинские выводы.

Распознавание произношения — отдельный экспериментальный модуль после основного MVP.

## Технические правила

- Kotlin.
- Jetpack Compose + Material 3.
- Gradle Kotlin DSL.
- ViewModel + StateFlow.
- Room для истории попыток и статистики.
- DataStore для простых настроек.
- Учебный алгоритм держать в чистом Kotlin-коде, не смешивать с UI.
- UI-тексты — на русском; имена классов/методов — на английском.
- Не добавлять тяжёлые фреймворки и сервер без необходимости.
- После появления стабильной базы не использовать destructive migration реальных данных без явного решения.

## Обязательное версионирование учебной логики

После M1 должны существовать и сохраняться вместе с данными:

- `learningPolicyVersion`;
- `curriculumVersion`;
- `databaseSchemaVersion`.

AI не вправе самовольно менять:

- пороги mastery;
- веса слабых/новых/старых букв;
- retry interval;
- критерии открытия уровней;
- правила определения weak letters;
- порядок/правила curriculum.

Если поведение меняется — требуется решение, запись в `DECISIONS.md`, соответствующая версия и обновление тестов.

## Правила изменения проекта

Для каждой задачи:

1. Провести Repository Preflight.
2. Коротко сформулировать план.
3. Убедиться, что задача соответствует `NEXT_TASK.md`/Issue и scope milestone.
4. Сделать минимальный законченный кусок.
5. Запустить доступные проверки и тесты.
6. Не оставлять заведомо некомпилируемый код.
7. Не отключать тесты/lint ради зелёной сборки без объяснения.
8. Проверить `docs/DEFINITION_OF_DONE.md`.
9. Просмотреть `docs/RISK_REGISTER.md`.
10. Обновить `PROJECT_STATUS.md`, если изменился фактический статус.
11. Обновить `docs/BACKLOG.md`, если изменился roadmap-status.
12. Обновить `docs/DECISIONS.md` только если решение действительно принято.
13. В отчёте отделить фактически сделанное от того, что ещё требует runtime/manual acceptance.
14. Перед закрытием milestone выполнить Milestone Closure Evidence Audit.

## Маршрутизация AI

Следовать `docs/AI_ROLES.md`.

- обычные GitHub/code/docs задачи → ChatGPT;
- commit/push/pull/обычный Run → простое действие владельца;
- Android Studio Agent → только IDE/SDK/Gradle/runtime/device/Logcat/TTS/Android-specific диагностика;
- pure Kotlin/JVM unit tests → ChatGPT, не Android Studio Agent.

## Git workflow

Следовать `docs/DEVELOPMENT_WORKFLOW.md`.

Главные правила:

- `main` должен оставаться рабочим;
- существенная кодовая задача — отдельная ветка/PR;
- не merge при красных тестах/build;
- не force-push в `main`;
- перед локальной работой синхронизироваться по `docs/LOCAL_GIT_SYNC.md`.

## Учебная логика важнее игровой оболочки

Нельзя прекращать повтор старых букв после прохождения уровня, открывать новую букву только за количество нажатий, много раз подряд повторять ошибочную букву, считать серию одинаковых вопросов устойчивым знанием или строить обучение на жизнях/наказаниях.

Метрики активности (`уровни`, `звёзды`, `минуты`, `серия дней`) нельзя использовать как замену метрикам знания из `docs/SUCCESS_METRICS.md`.

## Curriculum и distractors

Следовать `docs/CURRICULUM.md`.

Важно:

- не фиксировать правильный ответ в одном месте экрана;
- перемешивать позиции;
- различать потенциально похожие и фактически путаемые буквы;
- фактическая confusion matrix имеет приоритет при персональной тренировке.

## Privacy

Следовать `docs/PRIVACY_RELEASE.md`.

Никогда не коммитить:

- персональные данные ребёнка;
- аудиозаписи;
- локальную БД с реальной статистикой;
- signing keys;
- API keys/secrets.

## Критерий хорошего изменения

Владелец должен суметь получить изменения из GitHub, открыть проект в Android Studio, нажать Run, проверить функцию и описать наблюдаемое поведение.

Задача считается законченной только при выполнении соответствующего Definition of Done либо при явной фиксации того, какой acceptance-test ещё ожидается/какой критерий перенесён решением владельца.
